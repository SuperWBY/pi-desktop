# Pi Desktop 生产级路线图

**版本**：1.0
**制定日期**：2026-11-07
**目标平台**：macOS arm64 先行（Windows 只做浏览器自动化，桌面 Computer Use 明确不支持）
**引擎策略**：固定 pi 1.5.0 + 最小补丁
**产品形态**：RPA / 爬虫任务的「探索 → 编译 → 运行 → 验证 → 自愈 → 调度」闭环

---

## 0. 目标定义

### 0.1 一句话目标

到 **2027-04-24**，交付一个可对外分发的 macOS 生产版 Pi Desktop：用户可以描述一个网页或桌面操作任务，Agent 先探索并完成一次，再把过程编译成可版本化、可调度、可自愈的脚本资产；之后长期运行时不再消耗模型 token，出错时才唤回 Agent 修复。

### 0.2 北极星指标

| 指标 | 目标 | 性质 |
|---|---|---|
| 重复副作用（同一业务动作执行两次） | **0** | 硬门槛，任何一次即阻断发布 |
| 基准套件任务成功率（B1–B8，3 次中位数） | 逐阶段提升，P3 时 ≥ 85% | 发布门槛 |
| 已编译任务的平均 token 成本 | ≤ 探索模式的 5% | 产品价值证明 |
| 平均人工介入次数 / 任务 | P3 时 ≤ 0.5 | 可用性 |
| Crash-free session | ≥ 99.5% | 生产标准 |
| 失败原因可归因率 | 100%（无「未知错误」） | 可运维性 |

### 0.3 明确的非目标

以下内容**不做**，写进产品文档与用户协议：

- 验证码破解、滑块识别、人机验证自动通过
- 指纹伪造、设备伪装、代理池换号以规避封禁
- 绕过平台风控、速率限制或访问控制
- 把「能绕过检测」作为卖点或验收指标

替代能力是：**准确识别自己被拦 → 分类原因 → 停止并交还控制权 → 记录为可复现的基准数据**。原因见 §7。

## 1. 当前基线

### 1.1 已有能力（已验证）

- Electron 45 + React 19 + Vite 8 + TypeScript 7，主进程 `pi --mode rpc` 子进程 + JSONL 协议
- 多会话独立 Pi 进程，后台继续运行，切换不重启
- 三种浏览器后端统一路由：`inapp`（WebContentsView）/ `cdp`（专用 Chrome profile）/ `extension`（日常 Chrome + 扩展桥）
- 每次动作前强制重新观察，绑定 URL + documentId（extension 额外绑 tabId）
- SQLite 事务日志：写前落记录，响应丢失进入「结果未知」，禁止自动重试
- 文件选择暂停 + 文件名/大小/类型核对 + 可选 SHA-256
- 人机验证识别 → 暂停 → 人工接管
- macOS 原生 Computer Use（Accessibility + 截图 + CGEvent），桌面动作独立事务日志 + 进程生命周期保护
- 定时任务（cron / 时区 / DST / 文件变化 / 后台 tick）
- 73 个 `test-*.mjs`、47 个 e2e 场景
- 21 份实测证据（`docs/computer-use/evidence/`）

### 1.2 已知缺口

| 缺口 | 影响 | 处理阶段 |
|---|---|---|
| 工作树 45 改 + 106 新增未提交 | 无法回滚、无法协作、无法 CI | P0 |
| `src/main/project-trust-once.ts` 是空壳，测试必然失败 | 项目信任无法在应用内完成 | P0 决策 |
| README 版本号仍是 0.1.0 | 分发文案错误 | P0 |
| 无 `crashReporter`、无 `uncaughtException` / `unhandledRejection` | 崩溃无数据，无法定位 | P0 |
| 无自动更新 | 用户无法升级，修复无法触达 | P3 |
| 只有 ad-hoc 签名，无公证 | Gatekeeper 拦截，隐私权限每次重授权 | P3 |
| Playwright 浏览器未安装 | 浏览器类测试大面积跳过 | P0 |
| 无 CI | 回归靠手动 | P0 |
| 编译脚本无运行器 | 定时任务每次都跑完整 Agent，成本高且不确定 | P1 |
| 无统一证据存储 / 运行记录 | 无法回答「这次为什么失败」 | P1 |
| 无策略引擎（域名白名单、限速、并发） | 生产使用会触发平台风控 | P1 |
| 无基准套件 | 无法度量「更强」 | P2 |
| 无自愈 | 页面一改就永久失败 | P2 |

## 2. 产品架构

```
┌──────────────────────────────────────────────────────────────┐
│ Renderer（React 19）                                          │
│  任务库 · 运行中心 · 脚本审阅 · 轨迹调试 · 审批收件箱           │
│  基准实验室 · 能力与限制 · 设置                                │
├──────────────────────────────────────────────────────────────┤
│ Main（Electron）— 编排与持久化                                 │
│  Session Manager   多 PiProcess，后台会话                      │
│  Task Store        SQLite + 文件，任务契约与版本                │
│  Run Engine        队列 / 预算 / 取消 / 恢复 / 孤儿清理          │
│  Policy Engine     审批、域名白名单、限速、并发、审计            │
│  Evidence Store    截图、DOM 快照、网络摘要、下载物、回读结果    │
│  Trace Store       探索轨迹与运行轨迹，支持回放与对比            │
│  Update Service    签名更新通道 + 回滚                          │
│  Diagnostics       崩溃上报、诊断包导出                         │
├──────────────────────────────────────────────────────────────┤
│ Runners（独立进程，被监督，可杀可重启）                          │
│  script-runner    Node + Playwright(connectOverCDP) / 扩展桥    │
│  desktop-runner   computer-use helper                          │
│  shell-runner     沙箱内命令                                    │
├──────────────────────────────────────────────────────────────┤
│ Pi engine 1.5.0（RPC） + 我们自己的扩展                         │
│  policy extension（tool_call 拦截 + 参数改写 + 预算）            │
│  evidence extension（tool_result 采集证据）                     │
│  task skill（任务契约、编译规则、自愈流程）                      │
├──────────────────────────────────────────────────────────────┤
│ Backends: in-app · CDP Chrome · Chrome extension · desktop      │
└──────────────────────────────────────────────────────────────┘
```

### 2.1 两条执行路径（并存，按任务自动选择）

| | 探索模式（Explore） | 编译模式（Compile） |
|---|---|---|
| 适用 | 未知站点、一次性任务、流程不明确 | 已验证、需重复执行、需长期稳定 |
| 驱动 | Agent + `computer_use_session_*` | 确定性脚本，零模型调用 |
| 成本 | 高（token） | 接近 0 |
| 确定性 | 低 | 高 |
| 失败处理 | Agent 现场判断 | 分类 → 自愈 → 人工 |
| 产物 | 轨迹（可编译） | 版本化任务资产 |

**自动选择规则**：任何任务先以探索模式跑一次并留下完整轨迹。满足以下任一条件时，系统提议编译：
1. 同一任务被成功执行 ≥ 2 次
2. 用户显式选择「保存为任务」
3. 调度器需要周期执行

编译提议必须经用户确认，不允许静默把一次探索固化成生产脚本。

### 2.2 关键设计决策

1. **Runner 独立进程**：脚本崩溃、OOM、死循环不能拖垮应用。复用 `schedules.ts` 已有的「spawn + 超时 + killTree + 日志」模式，升级为可恢复的运行引擎。
2. **Playwright 只做库，不打包浏览器**：通过 `connectOverCDP` 连我们自己启动的 Chrome profile，避免 300MB 浏览器分发，也避免 Electron 内置 Chromium 与 Playwright 期望版本不一致。
3. **`codemode` 与任务脚本严格分离**：
   - `codemode`（pi 内置 QuickJS 沙箱）= 会话内多步编排，临时、不落盘、不承担生产责任
   - 任务脚本 = 持久资产，有契约、版本、测试、证据、回滚
4. **写操作必须先落盘再发送**：已有 `BrowserActionJournal` 扩展为通用 `ActionJournal`，覆盖浏览器、桌面、上传、表单提交、文件删除。
5. **证据优先于日志**：每次运行必须产出可独立核对的证据（截图、文件哈希、服务端回读），否则视为运行不完整。

### P1 — 执行内核 + 任务资产（2026-11-22 → 2027-01-16，8 周）

**目标**：让「一次执行」变成「可靠、可追溯、可复现的资产」。

#### P1.1 任务契约（Task Contract）

新增文件格式 `<project>/.pi-desktop/tasks/<slug>/task.json`：

```jsonc
{
  "slug": "acme-invoice-download",
  "version": 3,
  "name": "下载 Acme 上月发票",
  "intent": "登录后台，导出上月发票 CSV 到本地",
  "inputs": [
    { "name": "month", "type": "string", "pattern": "^\\d{4}-\\d{2}$", "required": true }
  ],
  "outputs": [
    { "name": "csv", "type": "file", "mime": "text/csv", "minBytes": 1 }
  ],
  "target": { "backend": "cdp", "origins": ["https://app.acme.example"] },
  "risk": "read" | "write" | "submit",
  "sideEffects": [
    { "kind": "download", "idempotent": true },
    { "kind": "form-submit", "idempotent": false, "dedupeKey": "invoiceId" }
  ],
  "successCriteria": [
    { "check": "file.hashMatches", "sha256": "..." },
    { "check": "server.readback", "query": "GET /invoices?month=..." }
  ],
  "limits": { "maxDurationMs": 180000, "maxSteps": 120, "maxTokens": 60000 },
  "policy": { "requireApproval": "first-run", "allowedDomains": ["app.acme.example"] },
  "createdFrom": { "traceId": "...", "sessionPath": "..." }
}
```

**设计要点**
- `sideEffects` 是核心字段：不可幂等的动作必须有 `dedupeKey`，运行引擎据此阻止重复提交。
- `successCriteria` 必须可独立验证，不允许「脚本跑完即成功」。
- `createdFrom` 保留可追溯性：每个脚本都能回到它被编译出来的那次轨迹。

#### P1.2 运行引擎

新模块 `src/main/runs.ts`，职责：
- 队列与并发上限（全局 + 每任务 + 每域名）
- 预算：时长、步骤数、token、下载字节
- 取消：协作式 + 强制 kill 进程树
- 崩溃恢复：应用重启后扫描未结束运行，按「未知状态」处理，必须先核对再决定继续
- 孤儿清理：runner 进程、临时 profile、临时下载目录
- 运行记录落 SQLite：`runs` / `run_steps` / `run_artifacts` / `run_events`

运行状态机：

```
queued → starting → running → verifying → succeeded
                          ↘ failed(reason)
                          ↘ unknown(需人工核对)
                          ↘ cancelled
                          ↘ timeout
```

`unknown` 是独立状态，不能并入 `failed`。

#### P1.3 Runner

新目录 `extensions/task-runner/`：
- `runner.mjs`：独立进程入口，读任务脚本 + 输入，执行，输出结构化结果
- `sdk/`：给脚本用的 API 表面
  ```js
  export default async function run({ page, assert, evidence, input, log }) {
    await page.goto('https://app.acme.example/invoices')
    await page.fill('label=月份', input.month)
    const file = await page.download(() => page.click('text=导出 CSV'))
    await evidence.file(file, { sha256: true })
    assert(file.size > 0, 'CSV 为空')
    return { outputs: { csv: file.path } }
  }
  ```
- 适配器：`cdp`（Playwright connectOverCDP）/ `bridge`（Chrome 扩展桥）/ `desktop`（computer-use helper）
- 沙箱策略（macOS）：默认禁止子进程与任意网络，网络经本地代理按 `allowedDomains` 放行；需要写文件时只允许任务输出目录

#### P1.4 证据存储

- 每次运行生成 `runs/<runId>/`：`manifest.json`、`trace.zip`、`screenshots/`、`downloads/`、`server-readback.json`、`report.md`
- 保留策略：成功运行保留摘要 90 天、证据 7 天；失败运行证据保留 90 天；可配置
- 所有证据带 SHA-256，报告可离线校验

#### P1.5 策略引擎

`src/main/policy.ts`：
- 域名允许列表（任务级 + 全局）
- 速率限制：每域名 QPS、每小时请求上限、并发上限
- `robots.txt` 检查（可配置为「仅警告」或「硬阻止」）
- 审批模式：`always` / `first-run` / `session` / `never`，按「域名 + 动作类别」组合
- 审计日志：`~/.pi-desktop/audit/<date>.jsonl`，不含输入值与页面文本
- 敏感域（银行、医疗、政务）默认硬阻止，需显式加入白名单

#### P1.6 统一审批收件箱

把现有的浏览器动作确认、桌面动作确认、文件选择接管、下载确认、权限申请统一到一个队列：
- 每条包含：任务、步骤、目标、将要执行的动作、风险等级、证据预览
- 支持键盘全流程操作
- 支持「本会话内对该域名读操作全部允许」
- 超时自动取消（不是自动批准）

#### P1.7 轨迹记录

探索模式产生的每次观察/动作都写入轨迹：
- 步骤序号、时间、动作类型、目标、观察快照摘要
- DOM 快照（可选全量）、截图、网络请求摘要
- 轨迹可在 UI 中回放；可作为编译输入

**P1 验收**
1. 故障注入 100 次（runner 被 `kill -9`、CDP 断开、浏览器崩溃、磁盘写满模拟），**重复副作用 = 0**
2. 10 个并发任务，无会话串扰、无日志交错、无凭据泄漏
3. 每个写操作在发送前都有持久记录；记录写失败时动作不发送
4. 运行中心能对 100% 的运行给出：状态、原因、证据、耗时、token
5. 一个完整任务（本地业务后台：查询 → 下载 → 转换 → 上传 → 提交 → 回读）在编译模式下执行，token 消耗 = 0
6. 应用重启后，未完成运行全部标记为 `unknown` 并进入待核对队列，不自动重试

**不做**：不做自愈、不做基准套件、不做自动更新。

### P2 — 编译与自愈 + 基准实验室（2027-01-17 → 2027-03-13，8 周）

**目标**：让脚本从「能跑」变成「会自己修」，并且用数据证明它在变强。

#### P2.1 编译（Trace → Script）

流程：
1. 用户点击「保存为任务」或系统提议编译
2. Agent 读取轨迹，生成 `task.json` + `script.mjs`
3. **静态检查**：类型检查、禁用 API 扫描（`eval`、动态 `require`、外网 fetch）、选择器稳定性评级
4. **沙箱试跑**：在隔离环境跑 1 次，必须通过 `successCriteria`
5. **差异审阅**：UI 展示脚本 diff、契约、每个选择器的来源轨迹步骤
6. **用户批准** → 写入 `v1/`，登记到任务库
7. **首次生产运行**强制人工确认

选择器稳定性评级（写进编译报告）：
- `getByRole` / `getByLabel` / `getByTestId` = 高
- 文本选择器 = 中
- CSS 路径 / XPath / 坐标 = 低（必须附替代方案）

#### P2.2 自愈

失败原因分类器（结构化，不允许自由文本作为唯一依据）：

| 原因 | 处理 |
|---|---|
| `selector_missing` / `layout_changed` | 触发修复任务 |
| `auth_expired` | 通知用户重新登录，暂停调度 |
| `challenge_detected` | 暂停 + 人工接管，不计入失败率 |
| `rate_limited` | 按 `Retry-After` 退避，不重试写操作 |
| `network_transient` | 只重试幂等步骤 |
| `unknown_outcome` | 冻结任务，要求人工核对业务结果 |

修复任务流程：
1. 取失败步骤的轨迹上下文 + 当前页面观察
2. Agent 提出**最小补丁**（只改受影响的选择器/等待条件）
3. 在沙箱中针对同一份夹具验证补丁
4. 生成 diff + 证据 + 风险说明
5. 用户批准（低风险任务可由策略自动批准）
6. 新版本生效，旧版本保留可回滚

**硬约束**：修复任务不得重放任何 `unknown_outcome` 的写操作。修复只改脚本，不补提交。

#### P2.3 基准实验室

新页面「基准实验室」+ 新模块 `src/main/benchmark.ts`。

**套件设计**（任务定义与评判器版本化、冻结）：

| 编号 | 类别 | 站点/夹具 | 验证点 |
|---|---|---|---|
| B1 | 静态抓取 + 分页 | books.toscrape.com、quotes.toscrape.com、scrapethissite.com | 条目数、字段完整率、去重、翻页终止 |
| B2 | 动态渲染 | demoqa.com、automationexercise.com、saucedemo.com | 等待正确性、模态框、异步列表 |
| B3 | 会话与表单 | saucedemo 登录、the-internet（auth / form / upload / download） | 登录态保持、表单值、错误态 |
| B4 | 文件流转 | 本地模拟后台（`scripts/fixtures/business-backoffice`） | 下载哈希、转换正确、上传哈希、提交次数 |
| B5 | 反自动化度量 | bot.sannysoft.com、creepjs、pixelscan、deviceandbrowserinfo | **只度量**：记录可检测信号，验证我们能识别并如实报告 |

**每次运行的记录**
- 模型、pi 版本、扩展版本、应用版本、提交哈希

**发布门禁**

- 报告必须包含失败案例，不允许只报成功

### P3 — 生产加固 + 首个正式版（2027-03-14 → 2027-04-24，6 周）

**目标**：可对外分发，用户能装、能升级、出问题能查。

**交付物**
1. **签名与分发（无公证）**：按 §8.1 执行——固定本地自签名身份、DMG 内安装脚本、首次运行放行向导、签名指纹可校验。不加入 Apple Developer Program。
2. **固定签名身份**：已有 `local-signing-identity.json` 机制，扩展为构建时强制校验；ad-hoc 只允许本地调试构建，正式构建必须使用固定身份。
3. **更新通道**：自建更新清单（JSON + SHA-256 + 签名指纹），应用内提示下载并校验，校验通过后引导用户替换。不做静默安装。
4. **首次运行向导**：检测 pi → 选择后端 → macOS 权限 → quarantine 放行说明 → 试用任务（本地夹具）→ 完成。
5. **诊断包**：一键导出（版本、日志、配置、运行摘要，不含页面内容与凭据），用于支持。
6. **数据治理**：
   - 设置 / 任务 / 运行记录 / 证据的 schema 版本号 + 迁移
   - 备份与恢复（导出 zip，导入校验）
   - 卸载清理脚本
7. **资源限制**：单任务内存上限、全局并发上限、磁盘配额与自动清理
8. **安全审查**：
   - 三个后端 + runner + 桥接的文件权限、token 生命周期
   - 凭据存储（`safeStorage` 加密）
   - 渲染层 CSP、`contextIsolation`、无 `nodeIntegration`
   - 依赖审计（当前仅 1 个运行时依赖，保持这个水平）
9. **文档**：用户手册、任务编写指南、限制清单、故障排查、**签名校验步骤**

**验收**
- 在一台全新的 macOS 机器上，从 DMG 安装 → 按说明放行 → 完成向导 → 跑通一个示例任务
- 从上一版本升级成功，TCC 权限无需重新授权（验证固定签名身份生效）
- 私自篡改的更新包被拒绝安装

- 安全审查清单全部关闭

### P4 — 持续优化（2027-04-25 起，长期）

### 4.3 交互原则（功能层面）

1. **任何不确定都必须可见**：结果未知时不允许显示「成功」或「失败」，只能显示「待核对」并给出核对入口。
2. **任何自动修复都必须可审阅**：补丁以 diff 形式出现，附风险说明，默认需批准。
3. **任何持续授权都必须可撤销**：在审批收件箱里能看到并一键撤销，附生效范围。
4. **成本必须可见**：每次运行显示 token 与估算费用；编译后成本下降要能对比出来。
5. **失败必须可归因**：不允许出现「未知错误」作为最终展示，必须有分类或明确标记为「未归类」并附带原始信息。

## 6. 技术风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| CDP 自动化易被识别 | 站点拒绝、任务失败 | 度量 → 报告 → 人工接管；修正**意外的**自动化痕迹（如 WebDriver 标志、缺失 UA-CH），不做设备伪装 |
| Playwright 与 Electron Chromium 版本差异 | `connectOverCDP` 兼容性问题 | P1 第一周做技术验证；只用库不打包浏览器；锁定版本 |
| Electron 主进程承载过重 | 卡顿、崩溃 | Runner 全部独立进程；主进程只做编排 |
| macOS TCC 身份随签名变化 | 每次更新要重新授权 | P3 固定签名身份 + 公证 |
| 长任务与关窗冲突 | 任务被中断 | 关闭即最小化到后台 + 后台 tick（已有基础）；显式提示「任务仍在运行」 |
| 沙箱逃逸 | 用户机器受损 | macOS Seatbelt / 容器；默认无网络出口，按域名放行；不执行未签名脚本 |
| pi 升级破坏兼容 | 功能回退 | 季度升级，配套兼容套件（扩展加载、RPC 命令、事件字段） |
| 基准站点失效 | 套件不可用 | 以本地夹具为主，公网站点作为补充；套件版本化，站点失效记为 `fixture_unavailable` 而非失败 |
| 脚本资产腐烂 | 长期维护负担 | 健康度 + 自愈 + 版本回滚 + 归档 |

## 7. 为什么不做「防风控绕过」

这条写进产品原则，因为它决定了产品的商业可行性：

1. **合规是入场券**：企业客户不会采购一个会导致账号被封、数据丢失、违反平台条款的工具。
2. **绕过是军备竞赛**：投入产出比持续恶化，且每次平台更新都会让能力归零。
3. **真正的差异化在可靠性**：能准确说出「我在第 12 步被 Cloudflare 拦了，需要你手动过一次验证，之后可以继续」的工具，比「猜自己成功了」的工具价值高一个数量级。
4. **可度量的诚实**：把「检测准确率」「安全交还率」「不重复提交」做成指标，是可审计的能力，而不是无法验证的宣称。

**因此产品提供**：检测、分类、退避、暂停、接管、审计、限速、域名策略、证据留存。
**产品不提供**：验证码识别、指纹伪造、代理池、账号池、封禁规避。

## 8. 已确定的决策（2026-11-07）

| # | 决策 | 结论 | 影响 |
|---|---|---|---|
| 1 | Apple Developer Program | **不加入** | P3 改为自签名 + 显式授权分发，见 §8.1 |
| 2 | `project-trust-once.ts` | **实现** | P0 内完成核心逻辑 + 应用内单次信任 |
| 3 | 默认后端 | **交互默认 `inapp`，脚本默认 `cdp`** | 写入 P1 的 backend 选择规则 |
| 4 | 遥测 | **默认关闭，纯本地记录**，用户显式开启才上传 | 崩溃报告只落本地；诊断包手动导出 |
| 5 | 首个正式版版本号 | **1.0.0** | 与 0.7.7 明确分界 |

### 8.1 没有公证时的分发方案（替代原 P3 计划）

公证（notarization）必须依赖 Apple Developer ID，因此在当前约束下改为：

1. **固定自签名身份**：首次构建生成一张本机代码签名证书（`Pi Desktop Local Signing`），私钥留在登录钥匙串，公钥随构建固定。这样应用签名身份在多次构建间保持稳定，macOS TCC 权限（辅助功能、屏幕录制）不会每次升级后丢失。
2. **DMG 内附带安装脚本与说明**：`install.command` 双击后执行
   - `xattr -dr com.apple.quarantine "/Applications/Pi Desktop.app"`
   - 打开系统设置引导页
3. **应用内首次运行检测**：若检测到 quarantine 属性或权限为 provisional，展示一次性配置向导。
4. **更新包完整性**：更新包用同一签名身份签名，并在下载后做 SHA-256 + `codesign --verify` 双重校验，校验失败拒绝安装。
5. **明确的用户告知**：README 与首次运行向导如实说明"本构建未经过 Apple 公证"，并给出校验签名指纹的步骤（`codesign -dv --verbose=4`）。

**代价（如实记录，不淡化）**
- 用户首次打开需要手动放行一次，无法做到"双击即用"
- 企业 MDM 批量部署会受限
- macOS 大版本升级后可能需要重新授权一次
- 无法使用 `electron-updater` 的静默安装，需要用户确认

若未来引入 Developer ID，只需替换 `scripts/mac-signing.mjs` 的身份来源并加一步 `notarytool submit`，其余流程不变——这是把 §8.1 设计成"可平滑升级"的原因。
